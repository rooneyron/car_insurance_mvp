## 三、service 的 system prompt 全文（模板 + 记忆注入）

### A 部分 = 原始模板（prompts.py L179-204，静态、所有 service 请求共用）
```
【角色定义】
你是一个车险售后助手，负责处理保单查询、已有保单相关问题、保险条款咨询以及人工服务转接。

【职责边界】
- 处理保单查询及已有保单相关问题
- 解答与车险售后相关的问题
- 在需要时引导或转接人工客服
- 不负责处理新的投保报价、保费计算等售前业务

【行为规则】
- 每次收到新的用户消息，都要结合当前对话状态、已有信息和当前消息，独立判断下一步如何处理
- 不要因为历史对话中已经出现过相关信息或工具结果，就机械跳过当前轮本应进行的处理
- 优先使用当前对话中已经提供的信息，不要重复询问用户已经明确提供的信息
- 当用户需要获取具体业务结果、保单信息或其他可由当前工具完成的信息时，应使用工具获取结果，而不是自行编造        ← L192（关键）
- 即使当前信息可能不完整，也可以根据可用工具的能力尝试处理；如果工具返回缺失必要信息，应根据工具返回的信息向用户补充询问  ← L193（关键）
- 用户补充信息后，应结合当前对话中已有信息继续完成当前业务
- 当用户询问具体保险条款时，必须使用可用的业务工具进行检索，禁止凭自身知识直接回答                              ← L195（关键）
- 工具返回结果后，必须忠实转述工具返回的内容，不得编造工具未返回的信息                                          ← L196

【输出风格】
专业、简洁、直接。
需要向用户追问时，只询问当前真正缺少的信息。

【拒绝边界】
超出车险售后业务范围的问题，明确说明无法处理，并根据情况引导用户转人工。
```

### 🔑 关键观察
1. **模板 A 里完全没有"如何使用长期记忆"的任何规则**——记忆是"外挂"上去的补丁。
2. 【用户相关历史】只标注「**可作为背景自然参考**」，措辞很弱，**没有授权 LLM"可据此直接作答"**。
3. 模板 A 的 L192/L195 却强力要求「**需要业务结果就用工具、禁止凭知识自行回答**」。
4. → 两者形成**直接张力**：LLM 把「出过险吗」当成"需要查证的业务结果"，认为必须调工具；而把记忆里的出险记录当成"仅供参考的背景"，不敢直接当答案用。

## 四、问题清单（分层归因）

### 问题 1｜语义记忆有现成答案，LLM 却弃用（核心）
- **现象**：记忆里明有「2025年出过追尾险」，LLM 不用来回答，反而去调工具。
- **根因**：
  - 模板 L192「需要具体业务结果…应使用工具，而不是自行编造」+ L195「禁止凭自身知识直接回答」→ LLM 把「用记忆作答」误判为「编造/凭知识」，不敢用。
  - 记忆块【用户相关历史】仅标「可作为背景自然参考」→ LLM 视其为"背景"而非"可引用的业务事实"。
  - 模板无任何"记忆可直接作答"的授权。
- **层面**：prompt / 记忆措辞层

### 问题 2｜系统没有「出险 / 理赔记录查询」工具（工具缺口）
- **现象**：service 只有 query_policy / search_insurance_terms / transfer_to_human，无出险查询工具。
- **根因**：工具集设计未覆盖"出险记录"这一售后高频意图。
- **层面**：工具层（能力缺失）

### 问题 3｜query_policy 能力与意图错配
- **现象**：LLM 拿 query_policy 硬凑"出过险吗"。
- **根因**：
  - query_policy docstring「查询保单详情…保单信息、保单状态」（chains.py L188）措辞宽泛，把"出过险吗"吸附过去。
  - policies.json 字段（保单号/身份证/姓名/车型/险种/保额/年保费/到期日/状态）**无出险记录**；query_policy_logic 的 success 返回（chains.py L114-126）里也没有。
  - → 即使查询成功，也**答不出"出过险吗"**。
- **层面**：工具定义 + 数据模型层

### 问题 4｜query_policy 参数契约不符「按人查出险」
- **现象**：缺 policy_id 直接 missing_params。
- **根因**：query_policy_logic 要求 policy_id + id_card **双必填**（chains.py L100-106）。但"我出过险吗"本质是**按人（id_card / user_id）查**，用户手里通常没有保单号。
- **层面**：参数契约层

### 问题 5｜missing_params 后回复仍导向保单查询（把用户引进死胡同）
- **现象**：回复「请提供您的保单号才能查询出险记录」。
- **危害**：
  - 用户问出险，却被要保单号（用户常常不知道自己的保单号）。
  - **更严重**：就算用户给了保单号，query_policy 查到的也只是保单基本信息、**无出险记录，仍答非所问**——这是个死胡同。
  - 话术「查询出险记录」暗示 query_policy 能查出险，与工具实际能力不符，**误导用户**。
- **层面**：话术 + 工具能力层

### 问题 6｜方向A确认句在 missing_params（查询未完成）时超前触发
- **现象**：查询没成功（missing_params，什么都没查到），回复仍说「本次查询**已使用**您留存的身份证…请确认」。
- **根因**：方向A措辞「若…**完成查询**，必须复述确认」，LLM 把"用了证件号当入参"直接等同于"完成查询"。
- **危害**：安全无害（是掩码值），但语义突兀——用户还没给保单号、什么都没查到，就被要求"确认查询用的身份证"。
- **层面**：记忆措辞层（方向A）

### 问题 7｜记忆注入与模板的整合方式是"外挂补丁"
- **现象**：记忆块声明"优先级高于简洁规则"，但该优先级**只对"确认句"生效**，对"是否该用记忆作答"毫无授权。
- **根因**：记忆是追加到模板末尾的补丁，模板主体规则（用工具 / 禁编造）仍主导 LLM 决策。
- **层面**：架构层（记忆与 prompt 的整合方式）

## 五、问题定性：为什么不是「单改 prompt」能解决

| 层面 | 涉及问题 | 单改 prompt 能否解决 |
|---|---|---|
| prompt / 记忆措辞 | 1、6、7 | 🟡 部分能（调整措辞、授权记忆作答） |
| 工具能力缺失 | 2 | ❌ 不能（需新增出险查询工具） |
| 工具定义 / 数据模型 | 3 | ❌ 不能（policies.json 无出险字段，需扩数据或加工具） |
| 参数契约 | 4 | ❌ 不能（需改 query_policy 或新工具的参数设计） |
| 话术 | 5 | 🟡 部分能（但根子在工具能力） |

**结论**：问题 1/6/7 可通过 prompt / 措辞缓解；但问题 2/3/4 是**工具与数据层面的能力缺口，非 prompt 能补**。
若只改 prompt（例如"允许用记忆答出险"），能让 S8 这个 case 治标通过，但"出险查询"作为一项真实业务能力仍然缺失——**当用户问一个记忆里没存的出险问题时，系统依然无工具可查、只能再次答非所问。**
