# 车险客服 Router 意图路由测试报告（L0–L3 生产全链路）

**测试日期**：2026-09-03
**测试对象**：Router 五层漏斗 `L0(安全) → DST(跨轮) → L1(关键词) → L2(小模型) → L3(大模型复核) → L4(澄清/转人工)`
**数据集**：`data/intent_eval_dataset.json`（84 条，工具可达性标注）
**测试入口**：生产路由主函数 `src/router/router.py::route_message`

> **结论速览**：生产有效成功率 **96.4%（81/84）**，真实失败 **3 条**（均为 L2 高置信判错，L3 无法介入）。

---

## 一、测试背景与目标

Router 采用五层漏斗做意图分类，其中只有 **L2（qwen-turbo 小模型）** 与 **L3（deepseek 大模型）** 会调用 LLM，L0/L1/DST/L4 均为纯规则层。

此前评测脚本 `eval_intent.py` 为聚焦意图判定，**直接调用 L2、跳过了 L0/L1**，导致两个问题：

1. 无法反映生产真实链路的模型调用次数与短路行为；
2. 部分能被 L1 关键词正确拦截的 query 被"冤枉"成 L2 错误。

本轮测试目标：**以生产真实链路 `route_message` 跑通全部 84 条**，验证 L3_PROMPT 修订效果，统计真实调用成本与成功率，并定位真实失败案例。

---

## 二、测试环境

| 项 | 配置 |
|----|------|
| L2 小模型 | qwen-turbo，temperature=0.1，dashscope 兼容端点 |
| L3 大模型 | deepseek，temperature=0 |
| 阈值 | `l2_accept=0.7`、`l2_review=0.5`、`l3_accept=0.6`、`l2_margin=0.4` |
| 判定口径 | 最终 `intent ∈ allowed_routes`（工具可达性数据集标注） |
| 单轮隔离 | 每条 query 使用全新 `RouterState`（`current_task=None`、`awaiting_slot=None`），不触发 DST 跨轮承接 |

---

## 三、测试经过（做了哪些测试）

### 测试一：L0/L1 短路统计（本地、零模型调用）

**目的**：确认真跑生产漏斗时，84 条里有多少会被 L0/L1 提前拦截、根本到不了 L2。

**方法**：对 84 条逐条调用生产函数 `check_safety`（L0）与 `check_keywords`（L1），纯本地关键词匹配，不调用任何 LLM。

**结果**：

| 层 | 短路条数 | 命中 query |
|----|---------|-----------|
| L0 安全 | 3 | 我要投诉、转人工、我要找客服 |
| L1 关键词(high) | 7 | 我要买车险、我想续保、续保多少钱、我要报案、理赔进度怎么查、可以加保吗、续保怎么弄 |
| **透传到 L2** | **74** | 其余全部 |

**结论**：预测真跑生产漏斗时，小模型调用应为 **74 次而非 84 次**（10 条被规则层短路）。

### 测试二：L3_PROMPT 修订

**改动**：

1. 套用新版语义化 L3_PROMPT（意图定义与 L2 对齐、增加 5 条复核要求、移除 `reason` 字段）；
2. **修复输出格式缺失花括号的缺陷**：`l3_reviewer.py` 使用 `.replace()` 而非 `.format()` 渲染模板，故补 **单花括号** `{"intent": "...", "confidence": 0.0}`。

**缺陷说明**：若输出格式缺花括号，模型可能照抄无括号格式，导致 `_parse_json_from_text` 三级解析全部失败 → 静默兜底沿用 L2 结果 → **L3 复核形同虚设**。

**兼容性核对**：移除 `reason` 字段安全——`l3_reviewer.py` 第 71 行使用 `parsed.get("reason", "")`，缺字段不报错，仅理由为空串。

### 测试三：生产路由全链路评测（真实调用 LLM）

**方法**：对 84 条逐条调用 `route_message`，用计数包装器 `CountingLLM` 统计 L2/L3 的真实 `invoke` 次数，将最终 `intent` 与 `allowed_routes` 比对。

---

## 四、测试结果

### 4.1 真实模型调用次数

```
L2 小模型 = 74 次   |   L3 大模型 = 7 次
```

与测试一的预测**完全一致**：10 条被 L0/L1 短路，只有 74 条真正调用小模型；其中 7 条触发 L3 复核（4 条采纳、3 条未过阈值落 L4）。

### 4.2 决策来源分布

| 决策来源 | 条数 | 含义 |
|---------|------|------|
| `l2` | 64 | L2 直接判定（conf≥0.7 且 margin 足够） |
| `l1_keyword` | 7 | L1 关键词直判 |
| `l0_safety` | 3 | L0 安全拦截 → 转人工 |
| `l3` | 4 | L3 复核采纳 |
| `l4_clarify` | 6 | 落 L4 澄清反问 |
| **合计** | **84** | |

### 4.3 成功率

| 口径 | 结果 | 说明 |
|------|------|------|
| 严格标签匹配 | **72/84 = 85.7%** | `intent ∈ allowed_routes`，把转人工/澄清也计为不匹配 |
| **生产有效成功率** | **81/84 = 96.4%** | 剔除 3 条 L0 转人工（生产正确）+ 6 条 L4 澄清（模糊输入的合理行为）后的真实通过率 |

## 五、失败与偏差案例分析

严格匹配下共 12 条不匹配，按**真实性质**分为三类：

### 5.1 类别一：L0 转人工（3 条）——非错误，生产正确

| query | 结果 | 判定 |
|-------|------|------|
| 我要投诉 / 转人工 / 我要找客服 | handoff（转人工） | 数据集 `required_tools=[]`，转人工本就是其正确归宿；仅因 `allowed_routes` 标注为 service 而在严格匹配下计为不匹配 |

### 5.2 类别二：L4 澄清（6 条）——模糊/垃圾输入的合理行为

| query | 类别 | 性质 |
|-------|------|------|
| asdfghjkl、。。。 | chitchat | 乱码输入，因判断原则 rule 7（乱码→general+较低 confidence）导致 conf<0.5 落 L4，属已知打分缺陷 |
| 那个、你帮我看看、我的车、怎么办 | ambiguous | 语义高度模糊，反问澄清是合理 UX；数据集标注为 general |

### 5.3 类别三：真实失败（3 条）——L2 高置信判错 ★重点

| query | 类别 | 应属 | L2 判定 | conf | 决策来源 |
|-------|------|------|---------|------|---------|
| 过户后保费怎么算 | sale_core | **sale** | service | 0.95 | l2 |
| 电子保单有效吗 | service_core | **service** | sale | 0.95 | l2 |
| 定损流程是什么 | service_core | **service** | sale | 0.95 | l2 |

**失败根因**：三条均属"**自信判错型**"——L2 以 0.95 高置信判错，且 top1-top2 margin 足够大（>0.4）。因此 L3 的两个触发条件（`conf∈[0.5,0.7)` 复核区间、`conf≥0.7 但 margin<0.4` 摇摆）**都够不着**，L3 没有机会介入复核。这是当前触发机制的结构性盲区。

---

## 六、关键验证结论

1. **调用成本预测坐实**：真跑生产漏斗为 **74 次小模型 + 7 次大模型**，而非"84 次小模型"。L0/L1 短路 10 条，与本地统计完全吻合。

2. **纠正了此前评测的两处"假错误"**：`我想续保`、`可以加保吗` 在跳过 L1 的旧评测中被判为 L2 错误；本轮真跑生产漏斗，二者被 **L1 关键词直接正确拦截**（sale / service），证明旧评测口径失真。

3. **L3_PROMPT 修订 + 花括号修复生效**：L3 被调 7 次、采纳 4 次（嗯 / 哦 / 我想问一下 / 可以吗 → general，conf 0.90~0.95）。这些置信度**高于 band 触发时的 L2 分值（0.5~0.7）**，说明是 L3 自身的有效判断而非解析失败兜底——花括号修复确有必要且已生效。

4. **打分稳定性旁证**：此前争议样本 `在吗` 本轮为 general 0.85（正常），未复现异常低分。

---

## 七、后续建议

| 优先级 | 事项 | 说明 |
|-------|------|------|
| 高 | 治理 3 条 L2 高置信判错 | margin/band 结构性抓不到，需从 L2 prompt 判定原则（如 sale/service 边界、rule 2 知识类问题归属）入手，或引入"工具需求反推"等差异化视角 |
| 中 | 修复 rule 7 打分缺陷 | 乱码/无关输入被判 general 时 confidence 过低（<0.5），导致落 L4 反问，UX 不合理；应让"确定不是业务"成为高置信判断 |
| 低 | 统一评测口径 | 建议评测同时输出"严格标签匹配"与"生产有效成功率"，并标注决策来源，避免转人工/澄清被误计为失败 |
